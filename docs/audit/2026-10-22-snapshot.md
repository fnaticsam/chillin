## Design and rollout constraints

The existing backend is a configuration store. Vercel documents delayed SDK replication, authoritative REST reads, and batch failure if any operation fails. Remediation uses authoritative reads for write decisions and a create-only position marker in each batch to serialize all related counters. It adds unique hashed email keys and create-only random referral keys. This is a bounded repair using existing credentials, not a new database or a live migration.

A later authorized rollout must stop old writers before enabling new writes: old versions do not honor position markers. Retain existing keys; lazy reads only accept legacy records when their stored email matches. Do not delete markers, reset counters, or run a bulk cleanup without a separate reviewed recovery plan. Prior corrupted records/counts require offline reconciliation. Signup quotas do not prove mailbox ownership or resist distributed traffic completely; a shared client limiter/bot protection and a transactional database remain recommendations. A global daily cap can also be exhausted by an attacker and needs product/operations review before rollout.

The duplicate-signup response still reveals membership and a public referral code to someone who knows an email. It is not account access, but data minimization/double opt-in is a future privacy decision. No verification or email delivery exists in this repository. Do not claim “verified” signups or use this response for privileges.
